# Online realm backups on the intended Windows host

Status on 2026-10-08: VSS capture, encrypted archive authentication, complete manifest verification and isolated PostgreSQL WAL recovery passed on the intended host. The copied cluster was stopped and the live game retained its uptime. This rehearsal had zero players; gameplay concurrency and pending-operation recovery remain unverified. Automatic creation task is prepared but not installed. Public testing remains closed.

Follow-up: six-hour creation task installed and its SYSTEM capture/handoff verified. Matching encrypted archive upload and downloaded SHA-256 verification passed under NT SERVICE\AOCHAINBackupUpload, with game uptime preserved. The first provider quota/throttle error did not recur on retry; no definitive root cause established. This supersedes the earlier installation-pending state. External alerts, gameplay concurrency and pending-operation recovery remain open.

The host preparation scripts take a Windows VSS snapshot of C: after the existing online world-save operation completes. PostgreSQL 16 data, WAL, game runtime, pending journals and private configuration are copied from that same immutable volume snapshot. There is no Stop-Service call or zero-player requirement. The world save remains the normal asynchronous character persistence operation; it may hold character guards during persistence and its latency needs measurement with gameplay.

This is a physical, crash-consistent backup, not a pg_dump archive and not a zero-loss promise. PostgreSQL replays captured WAL on restore. Updates that remain only in game memory are outside the snapshot. Filesystem links, external tablespaces and WAL on another volume are refused. Snapshot creation failure has no fallback to copying changing live files. Only the temporary snapshot created by the backup invocation is released; other restore points are preserved.

The existing encryption key is required and never regenerated or copied to cloud storage. The archive is authenticated by a decrypt-and-hash round trip. Plaintext staging and restore fixtures remain protected for diagnosis; disk usage must be monitored before scheduling. The upload service receives ciphertext only and must not read recovery keys or plaintext fixtures.

Successful future captures remove only their own authenticated plaintext staging after validating its absolute directory boundary and refusing storage links. Failed capture artifacts and restore fixtures remain protected for diagnosis. The prepared Windows task runs every six hours under SYSTEM, required for VSS, with scripts writable only by Administrators/SYSTEM, no saved user password, no simultaneous task instances and a one-hour deadline. It delivers the authenticated receipt and grants ciphertext read to the dedicated cloud uploader. The uploader independently verifies downloaded bytes and performs retention. Task creation does not verify its first SYSTEM execution or cloud completion; inspect both protected receipts. External failure alerts and local encrypted archive retention are still unfinished.

The new restore verifier checks archive authentication and all manifest file hashes, then starts the copied cluster on loopback port 55436. It changes configuration only in the new fixture, clears only that fixture's copied PID files, disables archive/restore commands and preload libraries, uses the snapshot's existing owner credential without printing it, and verifies the started process's data directory and port before stopping it. It never connects to the live database on port 55432 for restore or replays journals against the live API or Solana.

Before automatic creation is activated: run VSS and WAL recovery verification, rehearse pending journal states and idempotent receipt recovery, verify finalized chain reconciliation before reopening a restored realm, measure combat/inventory/save latency during capture, verify off-host retrieval and separate recovery-key custody, establish safe plaintext staging cleanup, and connect stale/failure receipts to alerts. Existing quiescent backup restore tooling does not accept this physical backup format.

References: [PostgreSQL filesystem snapshots](https://www.postgresql.org/docs/16/backup-file.html), [Windows shadow-copy creation](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/vsswmi/create-method-in-class-win32-shadowcopy).
