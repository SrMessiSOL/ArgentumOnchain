# Private realm recovery preparation

The intended Windows host has prepared `Backup-PrivateRealm.ps1`, `Test-PrivateRealmRestore.ps1` and `Test-DevnetPreparation.ps1` deliverables outside Git. They target only the new realm and preserve all prior realm state. They require an Administrator terminal for protected files/service control and PostgreSQL restricted-token execution. They are host-specific wrappers, not portable general installers.

Backup requires the public gateway disabled and zero players. It requests authenticated world save, stops the application services, creates a custom PostgreSQL dump, and captures private configuration, operation journals, NPC/runtime state, service configuration and map/NPC templates. A manifest records hashes and account/character/pending-operation/ledger counts. Application services are restarted in dependency order even after failure. The database service is never stopped or reset by backup.

`scripts/realm-backup-crypto.cjs` encrypts the tar archive with AES-256-GCM and a locally generated random 32-byte recovery key. Backup/key directories admit only Administrators and SYSTEM; the key never appears in console or Git. Authentication is verified by decrypting to a protected scratch file and comparing the original archive hash. Wrong-key/tampering/overwrite-refusal regressions pass. Plaintext scratch material is retained in protected storage for diagnosis; it is not an off-host deliverable.

Restore verification decrypts the matching backup, checks manifest file hashes, and restores with no original owners/ACLs into a separate PostgreSQL cluster on loopback port 55435. It compares database counts, stops the disposable cluster, and leaves the live realm untouched. Original environment files are never loaded into the test cluster. This does not test every ledger/escrow relationship or authorize resolving pending transactions.

Current evidence: crypto regressions and wrapper parsing pass. The first live backup attempt stopped, services recovered and no verified encrypted backup was produced. Stage diagnostics were added and the Administrator retry produced an encrypted archive with a matching authenticated round trip; services recovered. A full database restore and encrypted off-host copy are not yet verified.

The owner has no cloud backup account yet. Before onboarding players, establish an off-host destination, copy only the encrypted `.aobak`, verify its SHA-256 after transfer, and test retrieval/decryption. Preserve the recovery key separately in an offline recovery medium or secure vault; losing it makes the backup unrecoverable. Do not store an unencrypted recovery key beside the archive in the same cloud account, publish a sharing link, or paste keys/passwords into chat. No paid service was selected.
