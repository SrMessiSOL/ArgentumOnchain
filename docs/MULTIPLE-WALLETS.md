# Account wallets and independent ownership

One game account can link up to five Solana wallets. Each additional wallet signs its own exact account/session/origin/nonce/expiry-bound message, with a recent authenticated login. Linking does not require the original wallet, transfer assets, or submit a transaction. An address remains unique to one account. Legacy replacement endpoints retain their two-proof restrictions; the interface offers linking and connection selection instead of account-wide replacement.

The connected wallet selects the wallet for new operations. The frontend forwards a public address selection to the API; the address is untrusted and the API checks account membership on every use. Each committed operation stores its own wallet, and the isolated signer independently checks that membership. Changing the connection does not rewrite the default wallet, other sessions, listings, transactions or journals. The selection cookie is a preference, not an authentication credential. Multiple tabs in the same browser share that preference; wallet/transaction mismatch checks prevent signing a transaction prepared for another wallet.

Any linked wallet can mint a new unminted character. Finalized mint/stake/purchase history identifies the character's custody wallet. Character gold, exports and inventory settlements must use that owner wallet. Game admission verifies the finalized custody address and frozen NFT on devnet independently of the currently connected wallet. Registered NFT imports and staking also require actual on-chain ownership. Marketplace proceeds stay bound to the seller wallet in the listing; they do not follow connection changes. Account membership alone never conveys NFT ownership.

The wallet screen shows only linked wallets as cards, plus one Add wallet action until the five-wallet limit is reached. Cards show full public addresses and connected status. Selecting an existing card verifies that the extension returned that exact address; users must select the desired account in their wallet extension. Linking shows message approval and server verification states, then a completion modal. A validated server receipt updates the card immediately, independently of the optional follow-up refresh. The header refreshes verified membership when linking completes. Character cards display their recorded owner; operations for another wallet's character are disabled. Gold/character choices are limited to the selected wallet's characters. External NFT transfers can make a historical custody label stale until a successful stake/purchase; actual chain checks remain authoritative.

Installed validation: 13 disposable PostgreSQL tests, API/frontend compilation, offline signer policy and SDK lifecycle tests. Real browser linking/minting from a second wallet remains a user rehearsal; no wallet signatures or blockchain transactions were submitted automatically during this update. Existing authorities, assets and pending operations are preserved.

Frontend regression tests exercise additional-wallet challenge mode, exact-address receipt validation, rejection handling and approval/verification stages. These tests do not submit a real wallet signature.

Browser rehearsal found `wallet.reauthenticate` when adding a second wallet from an older session. The login page now accepts `reauth=1` to show the password form even when already authenticated; successful login creates a fresh session and returns to `/wallet`. This only changes the frontend redirect and does not relax the server recent-login requirement.
